# ADR 0039：自动配置有所有权证明的每网络 TAP-Windows 适配器

- 状态：已接受
- 日期：2026-09-13
- 取代：ADR 0012

## 背景

ADR 0012 要求用户为每个 Stella 网络手工配置并选择 TAP-Windows 适配器，这使多网络加入
依赖普通用户不应了解的 Windows 驱动工具。安装或修改签名内核驱动包仍是影响整机的管理
操作，但从已安装驱动包创建 root 设备具有更窄、可由客户端负责的生命周期。

友好名称不能单独证明设备所有权。多个客户端进程还可能在创建、打开、提交、回滚或删除
适配器时互相竞争，因此自动配置必须同时具备持久身份凭据和覆盖完整客户端操作的事务边界。

## 决策

已签名的 TAP-Windows Adapter V9 驱动包必须预先存在于 Windows Driver Store。Stella 不会
安装或移除驱动包，也不会持久修改 MAC、驱动 MTU 或重启微型端口。

`stella-tap` 通过 SetupAPI 为每个网络配置一个 root 设备。它创建硬件 ID 为 `tap0901` 的
网络设备，让 `DiInstallDevice` 选择已有签名驱动包，等待 `NetCfgInstanceId`，在驱动注册表
中写入包含规范接口 GUID 的 Stella 专用标记，然后设置连接名称。注册后的失败会删除半成品。
复用和删除前必须确认持久标记与设备当前接口 GUID 一致；只有友好名称匹配而没有该证明的
设备会被拒绝。

Stella 进程通过 Windows 命名 mutex 串行执行设备管理。参考客户端在完整的 `join`、`run`
或 `leave` 命令期间持有事务 guard，覆盖确保设备、配置、配置提交、回滚和删除。单线程
Tokio 运行时保证线程相关的 mutex 所有权在 guard 释放前不会迁移。

`stella-client` 将每个网络确定性映射为 `Stella <32 个字符的网络 ID>`。配置 schema v2
要求新写入或编辑的 Windows 网络条目使用该派生名称；v1 条目会先在内存中规范化，并在
下一次网络意图变更时重写为 v2。`join` 在使用加入凭据前确保设备存在；如果控制器加入或
本地持久化失败，会删除本次新建设备。`run` 会补建丢失设备。普通关闭保留持久设备；控制器
确认 `leave` 后会删除设备，并且即使设备清理失败也始终删除持久网络意图。

ADR 0012 的完整帧、重叠 I/O、取消、MTU 和介质状态行为保持不变。

## 后果

用户只需安装一次 TAP-Windows 驱动包。加入多个 Stella 网络会自动创建隔离、稳定的适配器，
Windows CLI 不再暴露适配器选择；离开网络只会删除持久身份能够证明由 Stella 创建的设备。

创建和删除仍需要提升权限。使用 Stella 派生友好名称但没有所有权标记的旧适配器不会被自动
接管或删除，管理员必须显式解决该冲突。同一时间只能有一个 Stella 客户端进程持有 Windows
TAP 管理事务。
